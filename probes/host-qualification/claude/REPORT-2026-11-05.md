# Claude Code host qualification — measured 2026-11-05

Claude Code **2.1.318**, headless `claude -p`, inherited authentication, session-scoped fixture MCP servers referenced by name from the `fixture-native` agent, in-band owner identity through the PreToolUse `updatedInput` hook. Parent model Haiku unless noted (`sonnet` rows were reruns after the Haiku parent missed the intended phase). The fixture is passive: it records what the host supplies and never cleans up its fake provider (worker, leaf, separately grouped grandchild). Every row is a measurement, not a cleanup qualification. Raw runs live under `runs/` (ignored by git); `analysis.json` in each run directory carries the per-call owner identity, hook events, signals, gaps and survival samples these rows summarize.

## Findings

1. **Owner identity is in-band.** Every child call reached the server with `thread` rewritten to the child's agent id by the PreToolUse hook; the identity-negative row shows a parent (ownerless) `send` refused with `NATIVE_OWNER_REQUIRED` while the child's calls in the same run resolved to its native owner. A forged non-empty `thread` from the parent was not exercised; the hook clears nothing today, so the Phase 3 hook must write the field unconditionally. The parent-side PreToolUse hook for `TaskStop` carries `tool_input.task_id`, which equals the stopped child's owner id (smoke: `a60897639fce0a7e9` in both).
2. **Cancellation is attributable only while a request is pending.** `TaskStop` during a pending `wait` produced `notifications/cancelled` with the request id and owner (smoke, stop-pending). A stop that landed in the dispatch-to-first-wait gap (126 s held) or between waits (116 s held) produced no signal at all. Normal child completion while execution was live produced `SubagentStop` and nothing to the server.
3. **No host action terminates descendants.** Worker, leaf and grandchild were alive at measurement end in every row with an execution: after cancellation, after `SubagentStop`, after graceful parent exit, after parent SIGKILL, and after the per-call timeout.
4. **Parent exit and crash.** Graceful exit: both servers received SIGINT about 235 ms before the host exited, with `SessionEnd`. SIGKILL: both servers received stdin EOF, no `SessionEnd`, no hooks after the kill.
5. **Loss of one server leaves other connections usable.** With the fixture server killed (SIGKILL or SIGINT), the control child's connection stayed usable and its pending request was cancelled with its own owner id; the observer kept working.
6. **The per-server `timeout` is a hard per-call wall.** A `wait` requesting 1980 s was cancelled at 1320.0 s in both the silent run and the run emitting progress every 10 s (132 frames). The child saw `MCP server "fixture" tool "wait" timed out after 1320s`; the server saw `notifications/cancelled` for the owner. Progress notifications do not extend it. Bounded waits below the per-server timeout remain required.
7. **Same-child resume works after a stop.** SendMessage to a stopped child reached the same native owner (smoke, stop-pending, stop-dispatch-gap, stop-between-waits). A completed child is resumable only when session persistence is on (measured separately in the Phase 1 acceptance run).
8. **Follow-up and steering to a busy child are queued, not injected.** SendMessage was accepted while the child's `wait` was pending (40 s), and the child acted on the message only after that wait returned (delivery delay 39.6 s and 40.1 s; `actedWhileFixtureWaitPending: false` in both rows). Parent messages therefore become visible between bounded waits, never inside one.
9. **Working directory.** The child reported and the server received the requested absolute cwd (cwd, cwd-inherited, cwd-symlink, cwd-change); missing, relative and nonexistent values were refused by the fixture before any execution started (cwd-missing, cwd-relative, cwd-nonexistent); an ambiguous request was reported rather than guessed (cwd-ambiguous).
10. **Healthy attachment gaps** with a Haiku or Sonnet parent: dispatch-to-first-wait 1.5–7 s typical, up to 18.5 s; between-waits 2–6 s typical, up to 20 s. Compaction, `/clear` and TUI gaps are unmeasured (TUI rows pending).

## TUI rows measured unattended

`clear` was driven through a pseudo-terminal (`script`) with the runner's input queue; a Haiku parent, 180 s child wait. `/clear` typed while the child's `wait` was pending produced `SessionEnd` with `reason: clear` and a `SessionStart` with `source: clear` and a **new session id** 0.5 s later. Both session-scoped MCP servers kept their processes: no SIGINT, EOF or cancellation reached them until the runner's cleanup, and the servers' inherited `CLAUDE_CODE_SESSION_ID` therefore went stale. The background child was not stopped: its pending call continued and it reached `SubagentStop` normally about 8.5 minutes later. Whether the new session can address the old child was not measured (the queued resume text was not submitted by the busy UI). On this version `/clear` is not a bridge-loss trigger.

## Headless-mode facts that shaped the harness

- A redirected `CLAUDE_CONFIG_DIR` answers `Not logged in`; authentication is inherited from the default config directory and only settings, MCP config and agents are isolated.
- A headless parent has no `TaskOutput`; a session whose only remaining work is a background child exits about ten minutes after the parent's turn ends (exit 0), cutting the child's pending call. Long waits therefore spawn the child in the foreground.
- A Haiku parent sometimes skipped the child and called the fixture itself, or never issued the stop within the wall bound; those rows were rerun with `--model sonnet`.

## Not measured here

The ten TUI scenarios (`/clear`, `/compact`, automatic compaction, settings-driven MCP restart, UI stop, TUI steering, native close, suspend/wake, clock jump, delayed callbacks) need an operator terminal; Codex desktop is a separate qualification. Nothing here measures a bridge cleanup implementation.

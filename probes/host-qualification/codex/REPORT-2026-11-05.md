# Codex CLI host qualification — measured 2026-11-05

codex-cli **0.166.0**, headless `codex exec` in an isolated per-run `CODEX_HOME` (only `auth.json` copied, removed after each run), the operator's configured model and effort (`gpt-6-astra`, `max`), the fixture MCP server preapproved per run, hooks enabled, native children spawned with `fork_turns="none"`. The fixture is passive: it records what the host supplies and never cleans up its fake provider (worker, command child, separately grouped grandchild). Every row is a measurement, not a cleanup qualification. Raw runs live under `.runs/` (ignored by git); each run's `analysis.json` carries per-call owner metadata, hook events, signals, phases and cleanup verification.

Rows before 13:59 UTC were the first batch; rows from 13:59 UTC onward ran after the account's usage window reopened (the earlier attempts of those scenarios failed instantly on the usage limit and are not listed).

## Findings

1. **Owner identity is in the metadata.** Every call carries `_meta["x-codex-turn-metadata"]` with `thread_source: user` for the root and `thread_source: subagent` plus a distinct `thread_id` for each native child; every child also gets its own MCP server process (identity row: three servers, distinct child ids, status sibling isolated). The bridge needs no hook for attribution; it must require `thread_source: subagent` for owner-bound calls.
2. **Cancellation is attributable only while a request is pending.** A child interrupt during a pending `wait` produced `notifications/cancelled` ("MCP response future dropped") for the owner's request (interrupt-wait, steer). An interrupt landing between dispatch and the first wait or between waits produced no signal (interrupt-dispatch-gap, interrupt-between-waits); normal child completion produced only the `SubagentStop` hook (child-complete).
3. **Hooks fire on Codex.** SessionStart, UserPromptSubmit, PreModelRequest, PostModelRequest, PreToolUse, PostToolUse, SubagentStart, SubagentStop, Stop and SessionEnd were delivered to plugin-level hook configuration with thread ids, transcript path, cwd and model in their payloads. SubagentStop therefore supplies the stop marker for a finished child.
4. **Owner exit and crash.** Graceful exit sends SIGTERM to the MCP servers (owner-graceful); SIGINT of the host cancels the pending owner request first (owner-sigint); SIGKILL gives stdin EOF with no SessionEnd (owner-sigkill). In no case were the fake provider, command child or grandchild terminated by the host; the harness's own verified cleanup removed them every time.
5. **Loss of one server** cancels the owner request that was pending on it while the sibling child's connection keeps working (server-sigkill, server-sigint).
6. **Follow-up and steering to a busy child** reach the same native owner; a follow-up sent during a pending wait was acted on only after that wait returned (`delivery_while_wait_pending: false`), the same queued behaviour as on Claude. After an interrupt, a steering `followup_task` was delivered and acted on (steer).
7. **Working directory.** The root cwd, the requested child cwd, the hook cwd and the server's own cwd were recorded and compared for a worktree and for a symlinked path (cwd-worktree, cwd-symlink); invalid values were refused before any execution started (cwd-validation).
8. **Same-child resume after an interrupt works** (interrupt-wait, interrupt-dispatch-gap, interrupt-between-waits, child-complete all show `resume-delivered` to the same owner).

## Headless-mode facts that shaped the runs

- The sandbox a companion job runs in blocks `ps`, so offline checks of process identity ran with a stub; live runs used the real `ps` and verified every recorded pid absent after cleanup.
- Two rows (`steer`, `cwd-symlink`) reached the harness wall after capturing their measurement; the wall is the harness's bound, not a host timeout.
- The root model occasionally ended its turn without spawning the child (first `followup-busy` attempt); the row was rerun.

## Long calls

`long-silent` (run 14:33:51 UTC): the child requested an 1800 s `wait` with `mcp_servers.fixture.tool_timeout_sec = 1320`. The server received `notifications/cancelled` ("MCP response future dropped") for the owner's request **1320.0 s** after the call; the child saw a tool timeout after 1,320 seconds and recorded that the execution and all three fake processes were still alive afterwards. `tool_timeout_sec` is therefore a hard per-call wall, the Codex counterpart of Claude's per-server `timeout`.

`long-progress` (run 14:34:21 UTC): the same 1800 s `wait` with the fixture emitting `notifications/progress` every 10 s (131 frames). The owner's request was cancelled at **1320.0 s** all the same; the child saw `timed out awaiting tools/call after 1320s` and the execution and its three fake processes were still alive afterwards. Progress notifications do not extend `tool_timeout_sec`. Bounded waits below that value remain required on this host too.

## Not measured here

TUI-only scenarios (`/compact`, `/new`, config-driven MCP restart, TUI stop key, automatic compaction, suspend/wake, clock observation) need an operator terminal; `native-close` depends on a native close affordance the harness could not find. Codex desktop is a separate qualification. Nothing here measures a bridge cleanup implementation.

# Copilot CLI as a host

Status — researched on `feat/copilot-host` at `31c569b`, 2026-11-23. Implementation and installed-product qualification are pending.

## Goal

A GitHub Copilot CLI lead can call `companion_catalog`, `companion_send`, `companion_status`, `companion_wait`, `companion_read` and `companion_cancel`. Send returns a thread immediately. When the companion finishes, the lead receives a short user message in the conversation that owns the thread.

## Decisions

1. Install one Copilot plugin. It bundles the existing `bridge-server/server.mjs`, the same six tools, an extension for notices and host hooks. Setup owns installation.
2. Jobs run in the background. Every live root lead gets the wake. Wait remains available. Native subagents own their threads and use wait, as specified in [THREAD_PLAN decision 16](THREAD_PLAN.md#decisions-2026-11-22).
3. Keep an open session's bridge alive while it owns work. Add a heartbeat only if Copilot actually unloads it. Closing the owning session follows the existing bridge-loss and recovery contract in THREAD_PLAN decisions 5, 10 and 11.
4. Nothing to install or implement inside a companion. The bridge marks the processes it starts to prevent recursive host loading.
5. The user accepts Copilot's experimental mode for this host. A profile setting works across launches.

6. **Setup enables experimental mode** (decided 2026-11-23, the user). Selecting the Copilot host runs Copilot's own `copilot config experimental true` and reports that it affects the whole Copilot profile. A plugin manifest cannot scope that switch to this plugin.
7. **Copilot's own approvals stay** (decided 2026-11-23, the user). The plugin ships no self-approval hook. The user approves once and saves the rule, or launches with `--allow-tool=agent-bridge`; installing the plugin never changes the user's permission policy.

## Design

**Package and setup.** Add the Copilot-specific legacy manifest at `.github/plugin/plugin.json`, a Copilot hooks file, and `extensions/notice/extension.mjs` in the checkout. Point MCP `args` at `${PLUGIN_ROOT}/hooks/launch-agent-bridge.sh`, pin `AGENT_COMPANION_HOST=copilot`, and set `timeout: 1320000` ms. The bridge caps wait at 1,200 s, leaving 120 s of headroom. Extend the existing dependency installer and host-path resolver. Put dependencies under the Copilot host state root (for example, `$COPILOT_HOME/agent-companion/deps`) since the legacy manifest received no `PLUGIN_DATA`. Reuse the repo marketplace. `setup.sh --host copilot` adds that local marketplace and installs `agent-companion@agent-companion` idempotently. Coordinate the shared `--host all` and registry change when the other host lands. Preserve the existing meaning of `both`.

**Experimental setting.** Under the recommended setup policy, enable the accepted prerequisite with `copilot config experimental true`. The interactive equivalent is `/settings experimental on`. Use Copilot's writer, which honors `COPILOT_HOME`. Its default is `~/.copilot`. GitHub documents no manifest switch to opt only this plugin into experiments, and the installed environment help listed no general experimental-mode variable. An unloaded extension cannot bootstrap itself. Check both the persisted setting and a live registration in doctor. Respect `extensions.mode` and individual extension disables. The measured `load_only` setting suffices. The CLI default `load_and_augment` also lets the agent manage extensions. Reversing the global switch is `copilot config experimental false`. Leave that user-wide choice to the operator on uninstall. [Extension guide](https://docs.github.com/en/copilot/concepts/agents/copilot-cli/about-cli-extensions) · [Configuration](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-config-dir-reference)

**Host identity.** Add `lib/hosts/copilot.mjs` to the existing registry. Use `$COPILOT_HOME/agent-companion` for state and `agent-bridge-` for the tool prefix. Resolve the default config directory as `~/.copilot`. Pass the controller's environment into `leadFromCall`. The plugin's narrowly matched pre-tool hook overwrites any caller-supplied `lead` using the actual hook's identifiers. Use the MCP environment as the root session and the trusted hook's `agentId` as the optional agent. Require matching root session on a root call and child session equal to agent ID on a subagent call. Missing or inconsistent identity fails closed for thread operations. Keep catalog's existing identity-free behavior. Do not infer a root call just because metadata lacks an agent ID. Keep `bridgePerSession` bound to the root for both callers. Reuse the existing ownership checks, hook result delivery and paging.

**Wake.** After `joinSession({tools: [], hooks: {}})`, the extension registers a local endpoint for exactly `session.sessionId`. Use a socket or named pipe with private access, a short session-derived name, and a private registration under the host runtime directory. Include an incarnation token so a dead extension cannot remove its replacement. The bridge routes the existing short `wakeNotice` to the recorded root only. The receiver verifies the ID, calls `await session.send(text)`, and acknowledges acceptance. Bound connection and send time, and do not blindly replay a send whose acknowledgement was lost. Preserve the existing result receipt until a read, wait or hook delivery claims it. A missing endpoint means `wake: null` with the reason and `fallback: companion_wait`. A live root gets a wake even when another session is in front. A subagent gets wait. Fresh sessions have no claim on an old session's results. Use session-start, prompt and post-tool hooks to deliver existing unread news to its owner.

**Lifetime and recursion.** The session owns the bridge. A switch keeps the old session loaded. Explicit close, process exit and crash use existing bridge-loss handling and fenced results. Qualify background idle retention with a real running job before shipping. If an *open* lead loses its bridge, implement and remeasure an activity/retention mechanism for the duration of running work. The extension's IPC alone is not evidence of a keepalive. Set `AGENT_COMPANION_JOB=<jobId>` in the shared controller-to-adapter spawn environment for every companion. For Copilot ACP also pass the measured `--disable-mcp-server agent-bridge`. A marked launcher must skip dependency work and bridge startup. Marked hooks and extensions return before registration. Keep the existing record-based recursion refusal as a second line of defense.

## Steps with checks

1. **Package and setup.** Fixture first, then installed product in a fresh home. One marketplace registration, one enabled plugin and one plugin-sourced MCP server after two installs. Check six advertised tools and dependency resolution. Disable, enable, update, uninstall. A plain new TUI joins with the saved setting. A disabled extension is correctly diagnosed.
2. **Identify the lead.** Implement descriptor and hook mapping. Check two simultaneous roots, two sibling agents, a nested agent, missing hook/ID and forged `lead`, including another root's thread reference. Status listings and reads must stay with the owner. Direct-call paths lacking provenance get `LEAD_REQUIRED`.
3. **Deliver results.** Connect the session endpoint to the existing completion path. Check idle and busy leads, a background session, simultaneous completions, late registration, stale endpoints and a racing wait. One accepted notice per completion in the normal path. Read still works after lost acknowledgement. Subagent send reports wait. Test the plugin alongside another installed hook.
4. **Verify lifetime and bounds.** Hold a real job through an idle hour and a background session switch, then complete it. Check pending work survives and only the original root wakes. Exercise `/clear` and full exit during work, inspect cleanup and the old thread's stored state. Run a full 1,200 s wait with the installed timeout, and cancel another wait while its job continues.
5. **Prevent recursion.** Check all five spawn environments. With the plugin and experiments enabled in the ACP companion's home, start and resume a companion job. Require zero nested bridges and wake registrations, and preserve the companion's unrelated MCP configuration.
6. **Qualify and document.** Run host, hooks, setup, delivery and registry guards, then the repo's complete suite. In an isolated installed-form TUI send, wait/read, follow up and cancel against the reachable local companions. In these runs Copilot filtered `COPILOT_PROVIDER_BASE_URL` and `COPILOT_OFFLINE` from the MCP child's environment. Supply the isolated local companion environments explicitly and verify their endpoints before making any live test call. Verify the state in the shared jobs view. Update README, ARCHITECTURE, CLAUDE.md, THREAD_PLAN and release readiness with actual coverage. Use of the operator's own Copilot profile is a separate live check.

## Risks

- Experimental is a profile-wide setting. The 1.0.114 `/experimental` screen warns that features can have bugs or disappear. Its screen listed seven command groups, including one-shot and recurring prompts, VS Code handoff, index and timeline search. The 16 feature flags included local model routing, autopilot progress checks, cloud/relay support, alternate diff, MCP Apps/Skills/Tasks, masked shell password prompts and deferred tool search. Commands and configuration also gate search/index features, detailed context accounting and dynamic workflows. Some require additional flags, entitlement or user action. Other enabled user, trusted project and plugin extensions can load too. `load_only` limits agent management across the profile and should not silently replace an existing preference. Re-run the probes after CLI upgrades. [CLI reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference) · [Workflow prerequisites](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/use-dynamic-workflows)
- A queued user message can run after the operator switches away. A closed session has no receiver. Rebinding its notice to the newly visible session would disclose another lead's result.
- A stopped or failed extension leaves usable MCP tools with degraded delivery. Report that on send and in doctor. An older release also had a dispatch hang after extension startup failure. Keep all six tools in MCP and test extension failure with a bounded wait. [Upstream issue](https://github.com/github/copilot-cli/issues/4670)
- Background idle retention, a 20-minute product wait, installed-product job cleanup and hosted-model behavior need release qualification. The measurements here used a fixture plugin and local inference.
